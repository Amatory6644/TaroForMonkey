# ТЗ v3: Telok — личная AI-контент-команда через Telegram

Дата: 5 октября 2026. Исходное согласованное ТЗ. Реализация начата; актуальный отчёт от 7 октября находится в [STATUS.md](../STATUS.md).
Основание: новое ТЗ пользователя про ChatGPT Plan и уточнение о контенте для одежды, специалистов, отелей и недвижимости.

## 1. Цель и границы

Владелец присылает в Telegram задачу, ссылки и материалы клиента. Система понимает запрос, собирает бриф, изучает доступные источники, предлагает идеи, готовит сценарии и промпты, а при подключённых генераторах производит и проверяет медиа. Возвращает результат и файлы в тот же диалог.

Telok — название приложения. Любой бренд/специалист/объект — отдельный проект с изолированными материалами и памятью. Отсутствие бренда не блокирует общие задачи: для них существует личный проект «Входящие».

Два режима:
- ASSISTANT: ответ, исследование, разбор документа, подготовка текста/плана.
- CONTENT_STUDIO: бриф → исследование → идеи → сценарий → производственный пакет → медиа → проверка.

Первая версия — личное локальное приложение одного владельца. Обслуживание внешних пользователей через их аккаунты, публичный SaaS и Android-приложение не входят в первый релиз. Создавать материалы для нескольких своих клиентов можно в отдельных проектах; право конкретного способа размещения на использование провайдеров проверяется перед распространением приложения.

## 2. Что подтверждено об использовании подписки

Официальный Sign in with ChatGPT описывает использование ChatGPT plan для подходящих Responses-запросов локального приложения. Это отдельное разрешение аккаунта пользователя. Токены текущего чата Codex не копируются, инструменты этого чата и его память автоматически не передаются боту. Доступ конкретного аккаунта проверяется реальным завершённым запросом. Источник: [Overview](https://developers.openai.com/siwc/token-sharing-open-source).

В текущем preview этого маршрута нет hosted image generation, file search и Code Interpreter; аудио/видео-ввод и transcription API также не поддерживаются. Поэтому обработка документов/поиск/транскрипция требуют собственных доступных инструментов, генерация изображений/видео — отдельного провайдера. Ограничения: [Preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations).

Seedance 2.5 — отдельная модель ByteDance. Её наличие подтверждено [официальной страницей](https://seed.bytedance.com/en/seedance2_5). Доступный пользователю endpoint, model ID, регион, цены и параметры API пока не проверены. До этого адаптер имеет статус NOT_CONFIGURED. Подписка ChatGPT не считается разрешением или оплатой Seedance.

Мой прежний список обязательных настроек проекта нужно уточнить: отдельный OpenAI API key не является обязательным для текстового маршрута при успешно подключённом ChatGPT Plan. Генерация внешнего медиа остаётся самостоятельной интеграцией.

## 4. Рекомендуемая архитектура

Telegram → приём и авторизация → TaskRouter → DBOS workflow → роли и инструменты → артефакты → ответ владельцу.

Роли обращаются к ReasoningProvider:
- ChatGPTPlanProvider — основной сильный текстовый/мультимодальный маршрут в пределах подтверждённых возможностей.
- LocalQwenProvider — опциональный локальный маршрут после проверки оборудования и качества.
- Старый OpenAI API provider сохраняется отключённым; автоматический платный fallback запрещён.

Медиа идут через отдельный MediaProvider:
- экспорт промптов и ручной импорт результата;
- SeedanceProvider после проверки реального API;
- провайдер изображений после отдельного подключения;
- существующие FFmpeg и локальная озвучка для сборки.

DBOS управляет бизнес-этапами. Модель не меняет статусы/бюджеты/права напрямую. У ролей структурированные входы и выходы. Для короткой задачи достаточно одного вызова; сложная задача запускает нужные этапы, без обязательного «совещания» всех агентов.

### Выбор runtime

Предпочтение для первого релиза: существующий официальный Python OpenAI SDK для OAuth-authenticated Responses streaming. Значение параметра SDK api_key здесь — OAuth bearer credential; это не отдельный Platform API key и не переключение оплаты. Каталог получать с учётом специальной схемы models/slug/display_name. Источник: [Models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference).

OAuth вынести в ChatGPTAuthService, использовать проверенную OAuth/OIDC-библиотеку с PKCE/JWKS, выбрать и закрепить версию при реализации. Не разрабатывать криптографическую проверку JWT самостоятельно. Официальный devkit @siwc/local — проверенный документацией альтернативный путь для Node-приложений; вводить Node sidecar только ради кнопки в существующем Python-проекте пока не требуется. [Пример devkit](https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt).

Изменение относительно исходного ТЗ: codex app-server не обязателен для MVP. Если понадобится выполнение локальных задач самим Codex, добавить CodexAppServerProvider: отдельный ограниченный процесс, stdio RPC, initialize/initialized, thread/start/resume, turn/start, terminal status и сохранение thread ID. Для env_key-конфигурации после обновления OAuth требуется перезапуск процесса и resume. Этот вариант официально документирован: [Codex app-server](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server). Он не должен становиться второй конкурирующей очередью бизнес-процессов.

## 5. Что передают друг другу роли

| Этап | Обязательный результат |
|---|---|
| Приём/бриф | TaskBrief: проект, цель, площадка, аудитория, формат, исходники, ограничения, желаемый результат, пробелы |
| Аналитик-маркетолог | ResearchReport: источники с датами/выдержками, факты, гипотезы аудитории, конкуренты, позиционирование, риски и пробелы |
| Креатор | ConceptSet: разные идеи с hook, сообщением, CTA, форматом, аргументом выбора и оценкой производственной сложности |
| Редактор/режиссёр | CreativeDirection: выбранная концепция, драматургия, визуальный стиль, ограничения продукта, причины отбора |
| Промпт-менеджер | ProductionPack: сценарий, сцены, референсы, промпты и параметры под конкретный provider/model |
| Производство | MediaJob + реальные assets, provider job ID, попытки, стоимость/неизвестный расход |
| Проверка | QAReport по фактам, брифу, сценарию, визуалу, речи/субтитрам и техническим параметрам |
| Выдача | ResultPackage: короткий итог, файлы, источники, ограничения, кнопки правок |

Промпт-менеджер — компилятор производственного задания, а не просто разрезатель текста. Для каждой сцены: стабильный scene_id, цель, длительность, герой/объект, действие, камера, свет, референсы, реплики, звук, экранный текст, ограничения, зависимости. Общие правила внешности персонажа, товара и пространства хранятся один раз и наследуются сценами.

Не задавать negative_prompt, seed, длительность или число референсов как универсально доступные: адаптер сверяет capability manifest выбранного провайдера. Текст/логотип по возможности добавляются при монтаже из утверждённых assets. Правка сцены пересобирает только зависимые результаты; смена общей стилистики инвалидирует весь зависимый набор.

## 6. Предметные требования

### Работа без бренда и с несколькими клиентами
- Личный «Входящие» для общих задач.
- Карточка клиента создаётся из сообщения; неизвестные значения остаются неизвестными.
- Ниша — шаблон брифа, а не отдельная кодовая ветка.
- Одежда: реальные товарные фото, цвет, крой, материалы, размеры; не подменять товар вымышленным.
- Специалист: подтверждённые услуги/квалификация; не придумывать кейсы и обещания результата.
- Отель: реальные номера/инфраструктура; художественные кадры не выдавать за фактическую съёмку.
- ЖК: подтверждённые характеристики/сроки/цены; визуализацию отличать от реального объекта.
- Память проекта не смешивается с другим проектом или общей памятью владельца.

### Свободные задачи
Поддержать ASK, RESEARCH, ANALYZE_DOCUMENT, WRITE, CONTENT_CAMPAIGN, GENERATE_MEDIA, EDIT_ARTIFACT. Для неизвестной возможности объяснить, какого инструмента не хватает. Нельзя отвечать «изучил сайт», если источник не был получен.

Исследование: реальный поиск, загрузка источников, безопасное извлечение PDF/DOCX/HTML, ограниченные размеры и время. Недоверенный текст источника не может менять права или команды системы. Retrieval сначала на PostgreSQL full-text, embeddings — только после измеримой необходимости.

До трёх критичных вопросов одним сообщением. Некритичные пробелы оформлять явными допущениями. Сохранять уточнения и продолжать тот же task_id.

### Telegram и домашний компьютер
- На первом этапе личный чат разрешённого владельца, long polling; публичный адрес домашнего ПК не нужен.
- Ответ на конкретное сообщение и кнопки привязываются к task_id/artifact_id/revision, а не только к «последней задаче».
- Одна обновляемая карточка этапа с ограничением частоты, /status, /cancel, /projects.
- Короткий итог в сообщении, большой отчёт — файлом; исходники/файлы по ограничениям Telegram.
- Голосовые — отдельная локальная транскрипция либо явно подключённый сервис, затем обычный TaskBrief.
- Выключенный ПК не выполняет задачи; после старта сверка очереди и информирование о состоянии.
- Ответ владельцу разрешён запросом. Публикация в канал сохраняет отдельное approval текущей версии.

### Авторизация и лимиты
- OAuth только в локальной панели и системном браузере на ПК.
- Постоянный непрозрачный host ID; раздельные аккаунт/workspace/client_id; одноразовые state/nonce/PKCE.
- Loopback callback, проверка подписи/issuer/audience/nonce и разрешения plan usage; код callback не логировать.
- Секреты в Windows Credential Manager/DPAPI под пользователем процесса; исключить из обычного backup. .gitignore сам по себе не шифрует данные.
- Отключение прекращает вызовы, очищает локальные секреты и пытается отозвать сессию; при недоступной сети сообщается непроверенный remote revoke.
- Refresh сериализуется одним владельцем сессии и атомарной заменой rotating token.
- Отдельные состояния: AUTHORIZED, PLAN_PERMISSION_MISSING, VERIFIED, LIMIT_REACHED, TEMPORARILY_UNAVAILABLE, REAUTH_REQUIRED.
- При лимите сохранять задачу. Переключать на Qwen только в разрешённом режиме и при достаточных capabilities; показывать смену провайдера.
- У подписки учёт вызовов/токенов/задержек отдельно от USD-ledger внешних генераторов. Не показывать выдуманный процент оставшихся лимитов.
- Никаких вызовов старого платного API при ошибке Plan. Доступ приложения к purchased credits проверить и ограничить в официальных Usage settings до пилота; при невозможности подтвердить ограничение автоматический запуск остаётся выключенным.
- Для Plus документация указывает общий пятичасовой лимит между приложениями: роли не получают самостоятельных квот. Детали авторизации/refresh/лимитов: [Sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [Accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions).
- Ограничить число шагов, запросов, времени и исправлений на задачу. Предварительно: 1 активный сложный workflow, максимум 12 модельных вызовов и 2 цикла исправлений; настройки корректируются по пилоту.
- Лимит времени/отмена не гарантируют отсутствие уже израсходованных токенов. Незавершённую внешнюю генерацию сначала сверять по job ID, не отправлять повторно вслепую.
- Ошибки сохранять с точным кодом/request ID и очищенной диагностикой; временная сеть не повод удалять credentials. [Errors and recovery](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery).

2. N07–N10: полный контент-пакет без обязательной генерации медиа.
3. N11–N14: локальный резервный маршрут, один видеогенератор, монтаж и QA.
4. Проверенный пилот; только затем расширение генераторов и автоматические кампании.

Старый T31 AUTO-публикации пока не приоритет. AUTO выбора провайдера и AUTO-публикации — разные настройки.

## 8. Приёмочные сценарии

1. Без бренда: «Изучи эти две страницы и сравни предложения» → сравнение с источниками и ограничениями.
2. Одежда: фото товара + задача → 3 идеи, выбранная концепция, сценарий и промпты без выдуманных свойств ткани.
3. Специалист: краткое описание услуг → бриф и контент-план; неподтверждённые регалии не появляются.
4. Отель/ЖК: материалы → ролик/пакет с разделением фактических кадров и визуализации.
5. Переключение клиентов: материалы A никогда не подмешиваются в B.
6. Лимит Plan: задача на паузе либо явно помеченный Qwen; платный API не вызван.
7. Refresh одновременно от двух задач: один refresh, валидная новая credential generation.
8. Обрыв потока: незавершённый ответ не выдан за готовый; retry ограничен и зарегистрирован.
9. Рестарт после submit видео: восстановление по job ID, без второго заказа.
10. Правка одной сцены: новая revision, повторная проверка, reuse независимых assets.
11. Сообщение неразрешённого пользователя: нет доступа к задачам, инструментам и аккаунту.
12. Злонамеренная инструкция внутри сайта/документа не меняет policy.
13. Отзыв доступа: корректная остановка; новая авторизация без потери проектов.
14. Полный live pilot: три разных ниши; владелец оценивает соответствие брифу, полезность идей и объём ручных правок. Целевой порог — ≥4/5 по каждой категории и ноль критических выдуманных фактов; до прохождения не заявлять стабильное качество.

Для N04 проверяются совместимые structured outputs; если выбранная модель/маршрут их не поддерживает — локальная Pydantic-валидация JSON с максимум одной попыткой исправления. Невалидный ответ не проходит дальше.

## 9. Что потребуется от владельца

Сейчас реальный бренд не обязателен: можно использовать явно синтетические учебные брифы трёх ниш. Для живого Telegram нужен bot token и Telegram user ID; для ChatGPT — личный вход и consent в браузере ПК. Пароль и OAuth-токены в чат не присылать.

Позже для настоящего видео: аккаунт выбранного провайдера, подтверждённый доступ API, бюджет и разрешённые исходники. До подключения выдаём честно обозначенный ProductionPack, а не обещание уже созданного ролика.

Сервер и отдельное Android-приложение для первого локального пилота не нужны. Оборудование для Qwen проверяется до выбора модели.
